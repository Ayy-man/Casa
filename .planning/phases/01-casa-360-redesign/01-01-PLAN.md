<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser localStorage -> client app | Demo "session" is read from `casa.auth.user` localStorage; no server validation |
| hardcoded email -> role value | `workspaceRole` is derived client-side from a hardcoded demo email in the `USERS` map |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-01 | Elevation of Privilege | `useRole()` / `workspaceRole` | accept | Role is a client-side UX signal only (greeting/pinning/prompts), not an authorization boundary. Phase 1 has no backend and no gated data — both demo accounts are full admins by design (CONTEXT.md "No financial gating in Phase 1"). Real auth + RLS is v2 (V2-AUTH/V2-RLS). Do NOT present role as a security control in code comments or UI. |
| T-01-02 | Spoofing | localStorage `casa.auth.user` | accept | Anyone can hand-edit localStorage to fake a session. Acceptable for a hardcoded-demo-creds milestone with no real data; documented in CLAUDE.md "Auth is fake". |
| T-01-03 | Tampering | `npm install date-fns` | mitigate | `date-fns` is a top-1000 npm package, MIT, no install scripts; pinned to `^3.x`. Single well-known dependency add — verify the resolved version in package-lock.json is an official `date-fns` 3.x release. |
</threat_model>
